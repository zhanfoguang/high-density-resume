# 岗位优势选择与简历编排

## 目标

当用户可写经历较多时，不把所有内容平均铺开。先建立完整证据库，再为一个具体 JD 选择最相关、最可追问且彼此互补的证据，形成 2–3 条岗位优势主线。

这里只评估“本次简历是否值得使用该素材”，不评价候选人的总体价值。

## 证据库字段

每条经历保留以下字段：

- `id`：稳定证据 ID，同一用户切换 JD 时保持不变；
- `source_fact`：未经美化的原始事实；
- `ownership`：主导、独立完成、参与或协助；
- `action`、`method`、`deliverable`：动作、工具/方法和结果/交付物；
- `strength`：`strong`、`medium` 或 `weak`；
- `defensibility`：`ready`、`needs-detail` 或 `conflict`；
- `distinctive`：是否具有真实、可解释且不挤占核心能力的差异化价值；
- `capability_tags`：该证据真正能证明的能力标签。

证据强度使用以下口径：

- `strong`：本人动作、方法、所有权和可验证结果基本完整；
- `medium`：存在真实行动，但范围、结果或证明材料不够完整；
- `weak`：主要是课程、证书、活动名称或自我评价，缺少实际应用证据。

## 岗位定位

基于核心证据生成定位，不先写口号再找事实。使用：

```text
专业基础 + 目标岗位最相关的工具/能力 + 有证据的工作方式或差异点
```

定位中的每个部分必须引用证据 ID。没有证据时删除，不用“学习能力强”“综合素质优秀”等空泛表达补位。

## 素材选择

将完成映射的 JSON 传给：

```bash
python3 scripts/select_resume_content.py mapping.json --max-core 3
```

四类决策：

| 决策 | 用途 | 默认位置 |
| --- | --- | --- |
| `core` | 直接支撑岗位主线，且事实可确认 | 简历前三分之一或首个核心经历 |
| `support` | 支撑加分项、迁移能力或补充维度 | 后续项目、实践或技能区 |
| `compress` | 与核心证据重复，或仅有低优先差异化价值 | 合并为一条或放入低优先区 |
| `hide` | 无岗位映射、事实冲突或不值得占用本次篇幅 | 不进入本岗位版本，仍保留在证据库 |

只有能力标签和岗位要求都没有新增时，才把较弱的重复证据压缩。两个项目使用同一工具，但分别证明不同岗位要求时，不得仅因工具相同而删除其中一个。

`needs-detail` 可以进入待确认区，但不得写入正式简历；`conflict` 必须隐藏并要求核验。

## 版面预算

- 先询问用户期望的一页、两页或指定模板；没有要求时，以可快速扫描和不牺牲核心证据为准，不机械强制页数。
- 在前三分之一呈现目标岗位、定位和 2–3 条核心优势证据。
- 每段核心经历保留 2–4 条互不重复的高密度表述；辅助经历通常保留 1–2 条。
- 多于四段经历时，按技术实践、业务实践、实习、开源或校园/社区等可扫描分组。
- 同一时期、同一项目或同一能力的碎片经历优先合并。
- 技能关键词必须落在能证明它的经历中；技能区只做索引，不替代证据。
- 保留一个真实且可解释的差异点，但不得让它挤掉岗位必需能力。

## HR 与机器筛选

- 使用教育、项目/实践、技能等常见标题，避免用复杂表格、图标、进度条或图片承载核心文字。
- JD 关键词只能自然落在能证明它的经历表述中；技能区只做索引，不用关键词堆砌冒充证据。
- 每个核心关键词检查“出现位置、对应证据、证据强度和仍缺什么证明”。
- 提醒用户导出后确认 PDF 文字可复制、可搜索，日期和层级关系没有因排版丢失。
- 不承诺通过 ATS，也不把关键词命中数当成人才评分。

## 五秒扫描

交付前检查读者能否在五秒内看到：

1. 目标岗位；
2. 两到三个核心优势；
3. 与 JD 对应的关键词；
4. 最强的可验证结果；
5. 这些证据对岗位或组织的实际价值；
6. 一个有证据的差异点。

如果看不到，先调整定位、排序和内容取舍，再润色句子。

## 多 JD 版本

同一用户只维护一份证据库。对每份 JD 独立执行要求拆解、覆盖率和素材选择，然后输出：

- 不随岗位变化的基础内容；
- 本岗位新增、上移、压缩或隐藏的素材；
- 每项变化对应的 JD 要求和证据 ID。

不要把多份 JD 的要求混成一个分数或一份模糊简历。
